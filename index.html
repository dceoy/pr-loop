Agent skills · Issue-driven development

From Issue to a reviewed PR — without the race conditions.

pr-loop is a set of four portable agent skills for GitHub-native development. Each skill does one job well, owns its own safety contract, and can be used on its own. Together, pr-loop composes them into a closed loop: implement → review → triage → re-review, until the exact final snapshot is reconciled.

Entry rule in the composite: if a PR already has published reviews or inline feedback — even on an older head — pr-loop starts with triage, not review. That decision is made once per PR. Stacked PRs are reconciled bottom-up; moving a lower layer invalidates downstream reviews.

The four skills

Three standalone skills own their mechanics. The fourth composes them without duplicating their policies. Pick a skill:

issue-to-pr — Implement Issues as reviewable PRs, then stop

Freezes the Issue set, repo instructions, target base and exact base SHA before planning, then produces a decision-complete plan: single (default), independent, stacked, or mixed — split only at independently reviewable responsibility boundaries, never just by size. Stacks are linear chains rooted at the target branch; dependency edges must be acyclic.

How it works

  • Reads what the task depends on first — AGENTS.md / CLAUDE.md, linked Issues, comments, referenced PRs, surrounding code & tests.
  • Implements each layer in isolation at the frozen base (roots) or verified parent head (layers), one active writer only.
  • Runs a real check before commit — tests, type-check, build, or the changed command itself. A syntax-only check doesn't count.
  • Publishes only fresh branches with create-if-absent semantics; never reuses or overwrites an unexpected ref.
  • Re-fetches Issues before each commit; if requirements changed materially, discards stale unpublished work and replans.

Contract

  • Stops after creating & verifying every PR. It does not review or triage them.
  • Default cap: 5 PRs (caller may override). An explicit split that can't be represented safely returns STATUS: blocked with one question — the smallest missing material decision.
  • Result: STATUS: complete | stopped | unsupported + ordered PR list (URL, base/head SHAs, parent, per-PR QA) and native-stack linkage status.
  • Native stacks need repo support + a stack-aware client (e.g. gh stack); otherwise it honestly reports an ordinary branch-based chain.

pr-review — One PR, one frozen snapshot, one verified review

Review-only. Freezes the exact base/head pair, binds all evidence to those commits, and publishes exactly one verified COMMENT review by default. It never approves, requests changes, merges, closes, or edits code without separate authorisation.

How it works

  • Risk-driven scope: picks the smallest review lenses relevant to the changed behaviour instead of reviewing everything shallowly.
  • Every candidate finding is tested against reachable code and counter-evidence. Only confirmed, non-duplicate defects of credible material impact are published — no padding a clean review with speculation.
  • PR text, comments and repo content are treated as untrusted evidence, not instructions.
  • dry-run / no-post modes return findings without mutating anything.

Optional security discovery

  • May invoke at most one already-available, trusted security-review skill, scoped to the frozen commits, with mutations forbidden.
  • Never installs a skill. If none is safely available, it does its own security lens and doesn't claim a scan happened.
  • If an invoked scan fails or is incomplete: fail closed.
  • Only pr-review deduplicates and arbitrates — one final review, not a pile of bot comments.
  • Result: STATUS: reviewed | unsupported | failed + REVIEWED_HEAD + published-findings count.

pr-feedback-triage — Reconcile feedback & CI on the live head

The counterpart to review's frozen snapshot: triage follows the current head. It reconciles every published feedback item and every completed CI failure — even when there is no review feedback at all — applies the smallest evidence-backed fixes, replies, and resolves only eligible threads.

Feedback discipline

  • Every item keeps its provenance (thread: / comment: / review: IDs) and gets a disposition: fix, already addressed, outdated, answer, clarify, defer, or won't fix.
  • Pushes use an expected-SHA conditional update (git lease / API compare-and-swap) — an unexpected commit is never overwritten.
  • An active CHANGES_REQUESTED stays awaiting_re_review until the same reviewer approves or dismisses it. A later COMMENTED review doesn't clear it.

CI discipline

  • Inspects check runs and the validated test-merge target (merge_commit_sha); unvalidated merge coverage is unknown, never “passed”. Missing checks ≠ passing.
  • After a fix, polls only the repaired checks — up to 15 min per new head, ≥30s apart — and requires fresh success on the new SHA. skipped/neutral don't verify a repair.
  • Never weakens gates or tests to go green. Unfixable targets end as explicitly abandoned with URL, attempted fixes and reason — not as a silent pass.
  • Bounds: 9 state-change restarts, 3 CI fix/push cycles per PR.

pr-loop ★ — The composite: run the whole loop to reconciliation

Composes the three skills across each PR in dependency order. It keeps an explicit dependency graph, an entry phase and a current phase per PR, and runs every required phase without asking for intermediate confirmation.

Procedure

  1. Resolve graph — from Issues via issue-to-pr (requires its verified complete), or a single existing PR / verified requested stack.
  2. Choose entry — published feedback exists → triage first; otherwise review.
  3. Review — reuse a prior review only if author/workflow provenance + persisted commit/base/head markers verify the exact current pair. Otherwise review fresh.
  4. Triage — feedback + completed CI failures on the live head.
  5. Reconcile & propagate — head/base moved → invalidate, propagate through the stack, re-review. Feedback only → triage again.
  6. Final pass — re-fetch the whole graph; one last triage per PR for fresh feedback/CI; complete only when everything reconciles.

Bounds & honesty

  • 3 review rounds / PR · 9 triage restarts / PR · 3 full-graph passes. Caller/runtime limits override.
  • Never merges, never clears reviewer state, never waits for third-party reviews or unrelated pending CI.
  • Result: success | stopped | unsupported with per-PR reviewed SHAs, rounds, restarts, propagation, CI status and per-check verified/abandoned outcomes.
  • Success ≠ merge-ready. Final CI status, branch protection and deployment checks are reported separately.

Core guarantees

These are the invariants that make an autonomous loop trustworthy. When one can't be held, the skills fail closed and stop — they don't improvise.

  • Single writerAt most one repo writer during a mutation phase; GitHub mutations are serialised against validated state.
  • Exact implementation baseissue-to-pr pins the target base and each layer's verified parent; only fresh, verified branches are published.
  • Frozen-head reviewReview analyses one immutable snapshot and publishes explicitly against that SHA.
  • Live-head triageTriage tracks current head/feedback, diagnoses completed current-head CI, and rejects stale prepared actions before mutating.
  • Model-directed recoveryTriage diagnoses recoverable failures itself and picks safe, bounded remediation — without relaxing QA or publication gates.
  • Final-head/base reviewAny head or base change after review forces another review of the affected snapshot before success.
  • Fail closedUnsafe state, stale state, unresolved QA/publication failures, exhausted mandatory limits, missing capabilities, actionable feedback, or an active CHANGES_REQUESTED all stop the procedure.
  • No third-party waitPublished bot/human feedback is triaged; pending third-party reviews and future comments are never awaited.
  • Bounded CI remediationOnly repaired checks are polled (≤15 min/head); each fix needs fresh SHA-bound success or explicit abandonment.
  • Completion ≠ merge readinessCI, branch protection and deployment status are reported separately. No protection is bypassed; no merge is implied.

Running it with remote Opus

The skills are model-agnostic — any capable coding-agent runtime with GitHub access can run them. Opus earns its place where the loop is judgment-bound rather than typing-bound.

Why Opus, specifically

  • Review arbitration. pr-review must separate real defects from noise, deduplicate by root cause, and resist being instructed by untrusted PR text. That's reasoning work — Opus's strength.
  • Triage diagnosis. “Model-directed recovery” means reading a failed CI log, forming a root-cause hypothesis, and choosing the smallest safe fix. A stronger model abandons less and guesses less.
  • Stack planning. Deciding single vs. independent vs. stacked — and where the reviewable boundaries are — is a design judgment made once, up front, with the whole Issue set in view.
  • Where Opus is wasted: mechanical propagation, polling selected CI, and re-fetching snapshots. Let the loop's deterministic bounds do that; spend Opus turns on review, triage decisions, and replans.
  • A practical split (the pattern this repo's author uses): plan & execute with a fast mid-tier model, escalate review/judgment to Opus — e.g. Claude Code's opusplan mode (Opus plans, a faster model executes, Opus advises at decision points).
  • Remote = the agent runs on a host you control (for example via an agent server on a home Linux box), works in a clone there, and returns results as real GitHub PRs/reviews. The skills don't care where the runtime lives — only that gh auth, git, and the loop bounds travel with it.

Three ways to put Opus on the loop

  1. Interactively, in Claude Code. Install the skills, then prompt with Opus selected. Best for a first run — you can watch the frozen snapshots, dispositions and bounds do their work. 
    claude --model opus
> Implement https://github.com/OWNER/REPO/issues/123 with pr-loop
  2. Headless / remote, one shot. Run the same prompt non-interactively on your remote host; the result contract (STATUS: … + SHAs + CI outcomes) is designed to be checked by a script or a second agent. 
    claude -p --model opus "Run pr-loop on https://github.com/OWNER/REPO/pull/456" < /dev/null
    Keep the finite bounds in the prompt if you need tighter ones — caller limits override the defaults (3 / 9 / 3).
  3. In CI, review-only, via the bundled reusable workflow. One Claude Code Action invokes the pinned pr-review skill once per frozen head; a separate API check afterwards requires exactly one new COMMENT review for that head, or the workflow fails. Note: the workflow relies on the skill to honour review-only instructions — it is not a separate read-only sandbox. 
    jobs:
  claude-code-review:
    permissions:
      contents: read
      pull-requests: write
      id-token: write
      actions: read
    uses: dceoy/pr-loop/.github/workflows/claude-code-review.yml@66193c0383663b48ea144b438d7dd4a42e02b6e2 # v1.1.5
    secrets:
      CLAUDE_CODE_OAUTH_TOKEN: ${{ secrets.CLAUDE_CODE_OAUTH_TOKEN }}
Remote-Opus checklist: authenticated gh on the remote host · repo clone (or API-based edits) with a single writer · the four skills installed in that runtime · finite bounds set · and a way to verify the returned REVIEWED_HEAD / FINAL_HEAD SHAs against GitHub before you call it done. If any mandatory capability is missing, expect STATUS: unsupported — that's the fail-closed contract working, not a bug.

Requirements

  • Git + authenticated GitHub access via gh or an equivalent integration.
  • A coding-agent runtime with repo/GitHub access and finite loop bounds.
  • For native stacked-PR linkage: repo support + a stack-aware client such as gh stack. The skills install nothing; without it you get explicitly-labelled branch-based dependent PRs.
  • Releases: SemVer tags are the source of truth (scheduled Mondays 09:15 JST + manual dispatch); skill ZIPs are attached to each release. No npm package is published.
